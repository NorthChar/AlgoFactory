## 决策来源与文档边界

用户先确认“那我们将主案例定为‘基于 BANKING77 的客服意图分类算法生成与验证’”，随后要求“可以，将这部分添加到主线中形成可追溯文档”。本记录保存这次范围调整及落实方式；技术细节为后续实现的规划，不是既有能力声明。

[原题](../source/exam-original.txt)的“任务 2”允许选择文本分类等具体行业场景，“加分项”包含同一框架用于表格分类和文本分类。“基础交付”只要求至少一个完整示例，因此客户流失兼容性测试不是基础要求，而是本次选定的质量保障与扩展性证据。

docs/source 保持原题和初始方案的原始快照，遵循其 [README](../source/README.md) 中“不追加说明、不纠正文字”和“后续变更记录在其他文档”的约定。当前实施以总体计划和本 ADR 为准；原始方案与当前主线的差异通过 Git 历史和决策记录追溯。Phase 1/2 已归档代码、数据及报告不重写为 BANKING77 证据。

## 背景、候选与选择理由

Phase 2 已完成客户流失 Mock 单候选的真实 Docker 闭环。用户希望依据公开数据质量重新选择主案例；此前比较了 BANKING77 与 Steel Plates Faults。

| 候选 | 支持该方向的证据 | 限制及本次决定 |
| --- | --- | --- |
| BANKING77 | 10,003 条训练数据、3,080 条测试数据、77 类；原始文本和意图易于展示；官方划分与论文可追溯 | 英文、限定类别；需要文本与多分类改造。选为唯一主案例 |
| Steel Plates Faults | 1,941 条、27 个特征、7 类；结构检查未发现缺失和重复；接近现有表格架构 | 没有原始图片和正常类别，少数类样本较少；本轮不实现 |
| 合成客户流失 | 已有运行、隔离、评分及回写证据 | 不代表真实业务效果；保留为轻量兼容性检查 |

BANKING77 的公开来源为 [PolyAI 官方仓库](https://github.com/PolyAI-LDN/task-specific-datasets)及[数据论文](https://arxiv.org/abs/2003.04807)，许可为 CC BY 4.0。初检原始文件 URL、文件大小和 SHA-256 已保存到[数据初检记录](../evidence/2026-10-28-dataset-audit.json)；检查范围及复现方法见[证据说明](../evidence/README.md)。实现导入时仍需固定上游版本并保留署名、许可，不依赖可变化的 master 分支重放。

选择理由是：客服输入输出容易理解，错误意图可以人工检查，适合展示知识检索、方案选择、候选比较及修复；与原表格案例结合，还能验证框架跨场景复用。此项选择不代表已有模型成绩更高，也不证明标签全部准确。

## 范围与不承诺的能力

主案例接收自然语言开发需求及英文客服文本数据，输出可运行分类代码、77 类已知意图的预测结果、独立评分及知识回写。首轮采用轻量 CPU 文本分类；TF-IDF 与 Logistic Regression / MultinomialNB 是待基线验证的初始候选，不预先承诺排名或性能门槛。

界面、说明和报告可用中文，原始任务数据保持英文。自动回复、对话机器人、中文客服效果、未知意图检测、真实工单系统接入和生产部署均不纳入本次范围。LLM 负责算法开发过程，生成分类器负责样本预测；不要求逐条通过 LLM 判定客服意图。

客户流失案例不扩充真实数据、独立业务界面或完整修复演示。主界面、Demo A/B/C 和主要交付报告围绕 BANKING77。原先 Phase 5 计划的轻量合成回归配置验证继续保留，不因本次决策提前实施或自动取消。

## 数据与评估计划

2026-10-28 结构初检：BANKING77 无缺失或空文本；训练集有 4 条归一化文本冗余、测试集有 1 条；训练/测试间有 7 个相同归一化文本，未发现同一归一化文本对应不同标签。归一化定义为首尾去空白、Unicode casefold、连续空白归一为空格；尚未核查语义近似重复和全部标签正确性。

实施顺序为先固定输入版本及以下数据处理规则，再运行模型：

1. 原始文件只读保存，记录来源、署名、许可、下载时间、上游版本和散列；保留原始行 ID 与处理后行 ID 的对应关系。
2. 官方测试集保持不变，测试集内重复记录单独披露。按上述固定归一化规则从训练数据移除与官方测试集相同的文本；训练集内部按相同文本及标签去重，若发现冲突标签则停止并报告。保存移除清单、原因及处理后指纹。
3. 从处理后的官方训练集划分训练/验证集，固定种子 42，初始比例 80/20、按类别分层，确保相同归一化文本不跨集合，所有类别均被覆盖。最终计数由导入脚本产生，不能直接按原始数量推算。
4. 文本词表、IDF 及其他学习到的预处理仅在训练集拟合；类别映射、评价规则、候选预算在运行前冻结。测试文本仅用于预先约定的去重检查，不参与词表拟合、阈值校准和模型选优。
5. 主指标采用 Macro-F1；同时报告 Accuracy、各类 Precision/Recall/F1、样本数和混淆情况。门槛由训练/验证基线校准并冻结，不能沿用客户流失的二分类门槛或查看最终测试成绩后调整。
6. 候选比较和修复只使用验证集。选定代码版本后最终测试一次；保存概率矩阵与类别顺序的对应关系，测试标签不挂载给候选代码。清理后的训练口径必须明确披露，不能默认与论文原始设置可直接比较。

## 兼容性检查及亮点的证据要求

客户流失使用已有合成数据、固定候选、种子与独立协议，检查解析、生成、Docker 训练、二分类输出、评分、报告和回写；按锁定环境与冻结容差验证指标。它应与 BANKING77 共用同一个核心编排入口和执行基础设施，以任务配置和适配器切换；复制两套编排器或单独运行未改造的旧版本不能作为框架复用证据。

共同入口的测试还须证明字段、标签映射、数据指纹、阈值和知识检索条件不会串用。数据类型或标签空间不兼容的经验不得直接应用到另一任务。历史 examples/phase2 只作为回归参考，新兼容性运行必须生成新的报告与代码版本证据。

| 亮点 | 必须提供的证据 | 不足以支持的结论 |
| --- | --- | --- |
| 框架跨场景复用 | 同一实现提交、同一编排/验证核心，表格与文本均真实运行并回写 | 仅保存两份独立脚本或旧报告 |
| 改造后的兼容性 | 新版本上客户流失固定案例持续通过，任务隔离检查通过 | 仅引用旧版本的 101 项测试 |
| 经验复用有效性 | Phase 4 的实际检索、使用轨迹及同条件对照 | 自动声称客服经验提高客户流失模型效果 |

本次选择覆盖需求 T02/T04/T05、A07、X08；BK01–BK08 将新增范围与阶段验收逐项关联。X08 从 out_of_scope 调整为 planned，范围仅为框架用于表格与文本分类，不包含跨业务模型效果或经验迁移提升的承诺。
