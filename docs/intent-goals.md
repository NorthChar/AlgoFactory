# 按业务目标开发咨询分类算法

本文对应 0.8.0，区分本次分类目标验证与旧 77 类案例。

## 用户怎样操作

1. 打开“创建算法开发任务”，选择开发目标。
2. 指定类别任务选择 2–76 个已有意图；单个意图识别选择一个意图。中文名称仅作辅助说明，保留原始英文标签。
3. 单个意图识别可选“兼顾识别效果与误报”或“优先减少漏判”。填写开发需求；离线入口提供与选择匹配的可编辑示例，自然语言入口允许日常表达和补充问答。
4. 完成理解/检查，核对目标、类别、样本数量、算法、评估偏好、修复次数、费用和运行方式。文字与选择不一致会阻止生成；未知类别、含糊目标或额外未支持要求需要修改或澄清。
5. 确认后生成代码。修改目标或运行配置会使旧确认失效。完成后在同一任务中查看结果、代码、训练与修复过程，并输入新英文咨询试用该模型。

自然语言理解每轮最多两次接口调用、最多三轮；代码生成预算另行设置。离线理解 + Mock 代码生成全程不调用 LLM，但训练、评分和试用由真实 Docker 执行。

## 三个目标的区别

| 目标 | 数据处理 | 输出及边界 |
| --- | --- | --- |
| 完整意图分类 | 原来的全部训练数据 | 77 类及对应概率 |
| 指定类别分类 | 仅保留所选类别在各原划分内的记录，编号重新映射到 0…K-1 | 仅能在所选范围内区分；未选类别不训练、不评估、不自动识别为“其他” |
| 单个意图识别 | 所选意图映射为正类 1，其余 76 类合为负类 0；总条数不变 | 两列概率；负类代表其他已知意图，不能视为任意未知业务检测 |

例如选择“银行卡丢失或被盗”是识别一条咨询的含义，不是在检测银行卡是否真的被盗，也不是交易欺诈预测。两个指定类别属于文本二分类；三个及以上属于文本多分类。

原数据全量训练 7,993、验证 1,999、最终测试 3,080 条。派生任务保留原 row_id 与划分归属，只筛选或转换标签；不重新混合划分。类名和顺序写入 labels.json / manifest.json。每次执行从固定版本原始材料重建预期内容，并核对文件散列，篡改处理文件后重写清单不能绕过校验。

## “优先减少漏判”如何生效

只适用于单个意图识别。默认方案按 Macro-F1、Accuracy 排序；优先减少漏判时：

- 逻辑回归使用 class_weight="balanced"，朴素贝叶斯使用 fit_prior=False；实际生成代码必须通过配置检查。这是固定的可审查策略，并不保证收益。
- 用对应目标的训练/验证数据建立独立参考基线，先冻结 Macro-F1 门槛及正类 Recall 门槛；通过门槛的候选按正类 Recall、Macro-F1、Accuracy、预设算法顺序排序。
- 二分类报告正类 Precision、Recall、F1、ROC-AUC，同时保留 Macro-F1 和 Accuracy。页面展示漏判、误报及各类样本数，不能用大量负类带来的高 Accuracy 掩盖漏判。
- 不调试最终测试集，不进行概率阈值搜索；低把握转人工、未知意图检测和准确率承诺仍未实现。

## 实现与追溯

ExperimentConfig 中的 goal / intents / objective 参与配置绑定（旧全量默认哈希兼容），规范化需求必须与配置完全匹配。LLM 的理解和复核都收到允许的原始标签及中文说明；用户确认后，工作台创建独立数据副本。CLI 也会为派生目标准备独立数据目录，并在读取 API 凭据前拒绝请求与配置错配。

同一编排器继续完成检索、规划、生成、静态检查、沙箱执行、评分、有限修复和回写。新增能力材料见 data/banking-intent-tasks.txt；原知识材料与历史证据保留。派生目标可以写回新验证记录，但暂不消费旧 77 类实验的总结经验。

任务报告和生成输入保存选择、类别顺序及配置哈希；模型保存时绑定代码、训练数据、环境与配置。错误分析和成果试用读取本任务的数据，不回退到全量数据或另一个任务的模型。相同算法骨架在不同任务中可能生成相同源代码，但其训练数据、标签映射、训练后的模型和验证协议不同；不能以代码文本不同作为唯一有效性证据。

## 复验

先按 README 准备依赖、BANKING77 数据和当前沙箱镜像。执行器有更新，需要重建镜像。

```bash
ALGOFACTORY_DOCKER_TESTS=1 python -m pytest -q
python scripts/verify_intent_goals.py --output-dir runtime/intent-goals-check
```

脚本创建四个真实工作台任务：全量、三个类别、两个类别、单个意图；检查配置绑定、训练、评分、回写和隔离模型试用。全部使用 Mock，不调用付费 API，默认不运行最终测试。显式加 --final-test 时，为三个派生任务各执行一次最终测试；全量任务仍只验证。最终测试失败不能改选候选。

[随仓库提供的验证摘要及 API 节选](../examples/intent-goals/README.md) 可直接查看；完整模型和中间预测保留在本机 runtime，源码中的复验脚本与测试可重新生成。新任务效果只适用于对应类别、数据和协议，不能直接与历史 77 类成绩比较。

## 本次验证摘要

见[结构化证据](evidence/2026-11-02-intent-goals.json)。完整回归307项通过，包含真实Docker；四种样例均完成模型试用。三个类别的最终测试Macro-F1为0.966553，两个类别为0.962494；银行卡丢失单个意图的召回优先方案在最终测试40条正例中识别35条、漏判5条，并在3,040条其他咨询中误报12条。这些是不同任务的成绩，不能直接与全量77类比较。

真实接口抽查总计8次：首次理解/复核2次因复核误解固定结构字段而阻止执行；补充精确功能说明后再次理解/复核2次通过；单候选生成4次完成训练、验证、回写和隔离试用。本次真实API样例只做验证集评估，未新增真实API最终测试，也没有验证所有标签组合。失败和成功摘要及生成代码节选随 examples/intent-goals 交付；完整运行保留在本机 runtime。
