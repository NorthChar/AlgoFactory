# AlgoFactory 总体实施计划

本项目面向 Mac M5 Pro 48GB 的本地演示，主案例为“基于 BANKING77 的客服意图分类算法生成与验证”，以此证明能力抽取、代码复刻、独立验证与知识沉淀的完整闭环。已有合成客户流失案例保留为轻量兼容性测试。该调整于 2026-10-29 经用户确认，来源、理由和范围见 [ADR-001](decisions/0001-banking77-main-case.md)。

当前已实现的是 Phase 1 知识基础和 Phase 2 客户流失单候选 Mock 闭环；BANKING77、多分类及改造后的兼容性检查均为 planned。真实 API 服务调用尚待配置与验证。docs/source 保持原始资料，当前计划通过 ADR 与原始要求、阶段证据关联。

## 问题定义与目标

输入为自然语言能力描述、CSV 数据、字段说明与任务约束；知识包含能力、适用条件、算法、依赖、历史验证和失败经验。输出为可加载 Python 实现、机器可读及中文验证报告、候选比较与版本轨迹，以及持久化知识更新。没有合格候选时明确失败，不能以代码生成完成代替算法验证通过。

主任务为英文客服文本的 77 类已知意图分类。首轮采用 TF-IDF 与轻量 CPU 分类器，Logistic Regression / MultinomialNB 作为待基线验证的初始候选；先完成单候选真实闭环，再进行至少两候选比较。客户流失只保留已有数据、固定候选和一条完整兼容路径，不扩充业务界面、真实数据或专门的修复演示。Phase 5 原定的轻量合成回归任务继续用于验证多任务配置。

范围外为生产部署、本地大模型训练、任意仓库抽取、Beam/MCTS、自动部署和大规模性能优化；本轮还不包括聊天机器人、自动回复、中文客服效果或未知意图检测。跨场景范围限于同一框架用于表格与文本分类，不承诺模型或经验跨业务迁移后的效果提升。

基础要求全部列为必须；进阶选择 CLI、Streamlit、多轮修复、候选比较、图谱展示、报告、回写、多任务配置及模板和指标插件。加分选择三角色协作、失败经验复用、能力版本、安全隔离、解释溯源及框架跨场景复用。X08 由 out_of_scope 调整为 planned，只有改造后的同一框架真实运行表格和文本任务才能签署该项，不能用两份独立脚本或历史报告替代。

安全边界、数据划分和独立验证从 Phase 1–2 落地，不能推迟到 Phase 5 才执行生成代码。各阶段通过退出检查后形成清晰 Git 提交。下一阶段开始前更新矩阵状态，范围变化需记录理由及受影响 Gate。

## 资源与可复现性

Python 3.11 作为首个验证版本，采用标准 Python 编排器，避免额外 Agent 框架成本。SQLite 降低运维成本，NetworkX 支持关系遍历与导出，scikit-learn 用于轻量 CPU 文本/表格分类，Streamlit 用于演示。无需购买服务器或训练本地大模型。LLM 通过显式 Provider 在 Mock/API 间切换，Mock 使用固定响应和可控故障，API 使用环境变量密钥，禁止静默降级。

初始预算为两候选、每候选最多两次修复、生成代码每次执行 120 秒、容器 2 CPU/4 GiB、禁网。预算为待基线实测的起点，不是硬件性能承诺。API 设置调用次数、超时及费用上限；日志脱敏。Docker 不可用时阻止真实生成代码执行，可展示 Mock 轨迹但不能签署执行验收。

主案例固定 BANKING77 上游版本、原始文件散列、许可和署名；去重、标签映射及划分规则先于模型运行冻结。官方测试集保留，按固定规则移除训练侧重复及跨测试重叠，再从训练侧按类别分层划分训练/验证（初始 80/20、种子 42）；详细规则见 ADR-001。以 Macro-F1 为主指标，并报告 Accuracy、逐类指标和混淆情况。客户流失兼容案例继续使用已有合成数据与 60/20/20 独立协议，不复用 BANKING77 的阈值。

两种任务均记录数据指纹、划分索引、模型配置与运行环境。词表、IDF 或表格预处理只在训练集拟合，候选及修复只看验证集；独立测试集在选定版本后一次评估。指标门槛先经训练/验证基线校准并冻结，禁止依据测试结果修改；不能把旧客户流失门槛当作文本任务门槛。

## 实施依赖与风险处理

后续顺序为 Phase 2.5 主案例适配与兼容性 → Phase 3 修复比较 → Phase 4 经验复用。Phase 2.5 须先扩展当前二分类输出和评分契约，再接入文本；不能复制独立编排器规避改造，也不能为新模型放宽静态检查、Docker 隔离或标签边界。API 不可用应记录 blocked 状态及重试条件，不把 Mock 当真实 API 证据。回写使用事务、稳定 ID 与幂等键；取消或超时保留可诊断状态。经验仅在真实重测后标为 verified，推测建议单独存为 proposed。

Phase 1 已基于 Python 3.11.16 / arm64 生成 uv.lock 及带散列的 requirements 文件，并验证知识层依赖。后续阶段加入新依赖时须更新锁文件并重新验证。GitHub 远端和发布仍在 Phase 6 配置。

## 评分证据与后续动作

技术能力 40% 由真实闭环、图谱检索、修复与统一验证证明；代码质量 30% 由契约、错误处理、日志、兼容测试及复现证明；创新性 15% 由三角色决策、经验复用对照及框架跨场景证据支持；完整性 15% 由矩阵、文档、UI 和交付样例证明。Phase 1 验收及限制见 [phase1.md](phase1.md) 与 [验证报告](../examples/phase1/verification.json)。历史 Phase 2 实现及验收边界见 [phase2.md](phase2.md)。下一步是落实 ADR-001 的 Phase 2.5；新能力全部保持 planned，Mock 闭环不代表真实 API 已验收。
