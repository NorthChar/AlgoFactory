# AlgoFactory：总体实施规划与 Phase 0 问题定义

我重新梳理了笔试题目的全部要求。我们需要完成的不是一个通用 Coding Agent，也不是一个简单的 AutoML 系统，而是一个以算法能力知识为基础、以自动验证为反馈、能够生成和持续积累算法实现经验的 AI Agent 原型系统。

我建议将整个项目分为 7 个阶段（Phase 0–6），先完成问题定义与技术设计，再逐步实现核心闭环、进阶功能和最终交付。

整体目标是：基础要求 100% 覆盖，选择有价值且能够可靠实现的进阶功能，再通过少量有技术含量的加分项体现创新性。

这些是我们的目标清单，不是当前完成状态。后面每个阶段都要用实际运行结果核验对应条目。

## 二、总体开发路线

1. Phase 0 — 问题定义与验收目标

   明确系统边界、场景、能力抽象、成功标准和演示任务。
2. Phase 1 — 系统架构与知识模型

   设计模块接口、Agent 状态、知识图谱 Schema、知识抽取和检索机制。
3. Phase 2 — 最小端到端闭环

   完成需求解析、知识检索、规划、代码生成、运行验证和知识回写。
4. Phase 3 — 自动修复与候选搜索

   实现错误分类、多轮修复、多算法候选比较与版本管理。
5. Phase 4 — 知识增强与经验复用

   完善成功/失败经验提取、检索、知识溯源，验证沉淀是否帮助后续任务。
6. Phase 5 — 交互界面与工程质量

   Streamlit、CLI、可视化、隔离执行、日志、测试、异常恢复。
7. Phase 6 — 集成验收与 GitHub 交付

   冷启动复现、示例运行、自动报告、文档、Git 提交与交付核查。

这里采用先闭环、再增强、最后集成验收的策略。Phase 2 完成时，我们就应该已经有一个可运行的基础系统，而不是等到所有加分功能完成后才能演示。

# 三、Phase 0：问题定义

这是目前应该首先完成的工作。我们需要回答五个问题：研究/工程问题是什么、系统处理什么输入、生成什么输出、允许哪些自主行为，以及如何判断系统完成任务。

## 3.1 项目背景与核心问题

传统算法开发需要人工完成需求理解、技术方案选择、算法实现、环境配置、测试与错误修复。这些活动依赖开发人员经验，而经验往往分散存在于算法文档、代码仓库和历史测试记录中，难以直接用于下一次开发。

现有 LLM 虽然能够根据自然语言生成算法代码，但单次生成仍存在三个问题：

1. 缺乏结构化领域知识约束：生成方案可能忽略数据条件、接口契约、指标要求或历史失败经验。
2. 缺乏独立、系统化的执行验证：代码语法正确不代表能运行，能够运行也不代表满足业务指标。
3. 缺乏可复用的经验沉淀机制：修复过程和评估结果未必能被组织为适用于未来任务的知识。

因此我们要解决的问题可以定义为：

> 如何构建一个知识与验证反馈驱动的 AI Agent 系统，将自然语言算法能力需求转化为符合接口规范、具有可验证性能的算法实现，并把执行结果与修复经验持续积累为可检索、可复用的能力知识？

注意，我们并不声称解决通用自动软件工程问题，而是针对受控的算法任务提供可复现的原型验证。

## 3.2 系统的正式定义

输入

\\(x=(d,\mathcal D,\mathcal C)\\)

其中 \\(d\\) 是用户自然语言需求，\\(\mathcal D\\) 是任务数据与数据描述，\\(\mathcal C\\) 是接口、指标、环境和资源约束。

已有知识

\\(\mathcal K_t\\)

包含算法能力、适用条件、代码模板、依赖、历史实现、验证结果与失败经验。

输出

\\(y=(c^\*,r^\*,p^\*,\mathcal K\_{t+1})\\)

其中 \\(c^\*\\) 是选定代码实现，\\(r^\*\\) 是对应验证报告，\\(p^\*\\) 是可追溯的执行与版本记录，\\(\mathcal K\_{t+1}\\) 是更新后的知识库。

系统的目标不是仅最大化模型指标，而是在功能、指标、资源和接口约束下，寻找一个能够通过验证的实现。

可以将其理解为：

\\[ c^\*=\operatorname\*{arg\\,max}\_{c\in\mathcal V} U(c) \\]

其中 \\(\mathcal V\\) 是通过强制性验证门槛的候选集合，\\(U(c)\\) 可以综合性能、运行成本和稳定性。若集合为空，系统应明确报告未找到合格实现，而不是返回未经验证的代码并声称成功。

这一定义还意味着：算法代码是结果之一，验证证据和知识更新同样属于正式输出。

## 3.3 确定行业场景与任务边界

主场景确定为 客户流失预测。在任务类型上，第一版聚焦结构化表格数据的二分类问题。

| 项目   | Phase 0 定义                                             |
| ---- | ------------------------------------------------------ |
| 业务场景 | 客户流失预测                                                 |
| 任务类型 | 监督式表格二分类                                               |
| 输入数据 | CSV + 数据字段说明                                           |
| 预测目标 | 客户是否流失                                                 |
| 候选算法 | Logistic Regression、Random Forest、HistGradientBoosting |
| 预处理  | 数值缺失、类别缺失、类别编码、特征缩放                                    |
| 算法评价 | F1、ROC-AUC、Precision、Recall                            |
| 工程验证 | 接口、异常、超时、资源、安全检查                                       |
| 生成结果 | Python 算法模块 + 依赖声明                                     |
| 验证结果 | JSON + Markdown 报告                                     |
| 历史记录 | 知识实体、运行记录、代码版本、经验条目                                    |

这里要明确两个范围：

范围内： 在现有 Python/scikit-learn 生态中，根据任务条件生成预处理与模型组合，修复代码，实现统一接口，并验证算法性能。

范围外： 从零发明机器学习算法、大规模模型训练、自动部署生产服务、无限制生成任意程序、保证任何输入任务都能成功。

此外，为满足题目中的“不同任务类型验证配置”，我们可以支持二分类与回归两种配置 Schema，但至少需要提供真正运行的对应测试，不能只在代码中预留名称。如果进度允许，再加入一个轻量回归任务作为跨任务演示。

## 3.4 明确 Agent 的自主决策范围

系统不应该把每一步都交给 LLM 自由决定。应让 Agent 负责具有不确定性的决策，让程序负责确定性执行。

| 环节      | 执行方式               |
| ------- | ------------------ |
| 需求理解    | LLM 提取 + Schema 校验 |
| 知识检索    | 结构化过滤与检索           |
| 方案规划    | LLM / Mock 策略      |
| 代码生成    | LLM / Mock 模板      |
| 代码安全检查  | 确定性规则              |
| 代码执行    | 隔离运行器              |
| 测试与指标计算 | 确定性验证器             |
| 失败分类    | 规则优先，LLM 辅助解释      |
| 修复/切换决策 | 有边界的 Agent 策略      |
| 经验提取    | 结构化规则 + LLM        |
| 知识与版本回写 | 确定性存储模块            |

Agent 可选择的核心动作限定为：

- `GENERATE`：根据规划生成初始实现。
- `REPAIR`：处理明确的代码或接口错误。
- `OPTIMIZE`：针对未达标的指标提出改进。
- `SWITCH`：切换算法候选或实现方案。
- `ACCEPT`：接受通过验证的实现。
- `STOP`：达到预算或无法继续改进时终止。

每次决策都必须有来源明确的状态和证据，例如异常堆栈、未满足的约束、候选指标或历史修复记录。

这能够体现 Agent 的自主性，同时避免把系统做成难以调试的无限循环。

## 3.5 定义完整的成功标准

我们需要区分三种“成功”，否则 Demo 很容易只展示一个好看的执行流程。

功能成功： 系统能够解析需求、检索知识、生成代码并执行。

算法成功： 生成代码通过强制性功能、接口、稳定性与指标验证。

闭环成功： 验证与修复结果能够持久保存，并能在后续任务中被检索使用。

建议采用以下验收标准。

| 验收对象   | 最低标准                |
| ------ | ------------------- |
| 端到端流程  | 至少 1 个完整成功案例        |
| LLM 适配 | API / Mock 共用工作流    |
| 知识抽取   | 文档生成结构化实体与关系        |
| 知识检索   | 能引用检索到的能力和经验 ID     |
| 代码生成   | 生成真实 `.py` 文件，可独立加载 |
| 自动验证   | 四类验证均有可执行检查         |
| 修复能力   | 至少 1 个错误被修复并重新验证    |
| 候选比较   | 至少 2 个候选在相同协议下比较    |
| 经验沉淀   | 保存成功、失败与修复记录        |
| 经验复用   | 后续运行能够检索并利用已有经验     |
| 版本管理   | 能追溯父版本、修改原因与验证报告    |
| 复现性    | 固定数据、随机种子与依赖        |
| 安全性    | 执行前检查、隔离、超时和资源限制    |
| 可用性    | CLI 与 Web 均可完成主要演示  |
| 工程质量   | 自动化测试通过，无关键未处理异常    |

对数值指标，不预先编造 F1 或 ROC-AUC 成绩。项目可设置明确的验证门槛，但必须通过基线实验确认门槛合理，再在独立测试数据上报告实际结果。

# 四、总体系统架构

建议采用一个统一的编排器 + 三个职责明确的 Agent + 确定性工具模块。

这样可以满足多 Agent 协作的加分方向，又不会引入复杂的消息通信框架。

User Interface

CLI / Streamlit · 算法描述、数据、约束

Agent Orchestrator

运行状态 · 决策边界 · 任务预算 · 日志

Knowledge Agent

抽取、检索、证据组织

Builder Agent

方案规划、生成、修复

Review Agent

诊断、解释、建议动作

Deterministic Tools

Knowledge Retrieval

Sandbox Execution

Validation Engine

Version & Report Store

Knowledge Repository

SQLite + NetworkX · 能力、版本、验证、经验

检索复用 · 验证反馈 · 经验回写

这里有两个关键设计约束。

首先，Review Agent 可以解释失败并提出动作建议，但不能修改验证标准。验证器独立于 LLM。

其次，不将知识图谱仅作为可视化展示。规划器需要真正读取图谱中的适用条件、依赖和历史经验，验证结果也要关联回具体实现版本。

## 五、核心知识图谱 Schema

采用 SQLite 存储实体和关系、NetworkX 进行图遍历与可视化。两者共享统一的数据模型。

| 实体               | 主要字段                                   |
| ---------------- | -------------------------------------- |
| `Task`           | task_id、task_type、constraints          |
| `Capability`     | capability_id、description、input/output |
| `Algorithm`      | algorithm_id、family、applicability      |
| `Implementation` | implementation_id、version、code_hash    |
| `Dataset`        | dataset_id、schema、fingerprint          |
| `ValidationRun`  | run_id、metrics、status、config           |
| `FailureCase`    | failure_id、category、root_cause         |
| `Experience`     | experience_id、condition、action、outcome |
| `Dependency`     | package、version_constraint             |

主要关系包括：

- `Task → REQUIRES → Capability`
- `Algorithm → IMPLEMENTS → Capability`
- `Algorithm → APPLICABLE_TO → Task`
- `Implementation → USES → Algorithm`
- `Implementation → DEPENDS_ON → Dependency`
- `ValidationRun → EVALUATES → Implementation`
- `ValidationRun → USES_DATASET → Dataset`
- `ValidationRun → REPORTS → FailureCase`
- `Experience → DERIVED_FROM → ValidationRun`
- `Implementation → DERIVED_FROM → Implementation`

每个经验条目都必须能够追溯到真实验证记录，避免将 LLM 推测的修复建议直接当成已证实的知识。

# 六、分阶段实施计划与验收标准

Phase 0

当前

问题定义与需求冻结

确定场景、输入输出契约、系统范围、成功标准、演示案例与功能优先级。

交付：问题定义、需求矩阵、验收标准、示例任务规范

验收：每一条基础交付要求均有明确的实现模块及测试方法

Phase 1

系统架构与知识构建

实现 Schema、数据库、文档知识抽取、实体关系校验、知识检索、Mock/API 抽象层。

交付：知识库、抽取结果、图谱导出、LLM Provider 接口

验收：文档能够转换为结构化知识；实体可查询、关系可追踪

Phase 2

最小 Agent 闭环

实现需求解析、知识检索、方案规划、代码生成、独立执行、测试和验证回写。

交付：可运行的 CLI、代码生成样例、首份真实验证报告

验收：Mock 和 API 两种模式走通相同的核心流程

Phase 3

候选搜索与自动修复

加入功能错误与指标不足分类、修复循环、多候选比较、版本选择与停止条件。

交付：修复轨迹、候选排名、版本记录

验收：可以演示真实失败→修复→重测；不同候选采用统一验证协议

Phase 4

知识增强与经验复用

将失败诊断、修复动作和效果结构化存储，并在后续任务中检索和利用。

交付：经验条目、检索证据、复用实验与对照报告

验收：证明一次历史经验被后续任务使用，且不依赖隐藏提示或硬编码

Phase 5

界面、安全与工程完善

完善 Streamlit、图谱展示、报告、Docker 隔离、日志、异常处理、配置与自动化测试。

交付：Web Demo、安全执行环境、单元和集成测试

验收：正常、失败、超时及异常数据场景均有预期行为

Phase 6

最终验收与交付

完整运行演示、冷启动复现、整理文档、依赖锁定、清理密钥、审查 Git 记录并提交 GitHub。

交付：正式仓库、README、示例数据、测试、报告及演示说明

验收：全新环境依据 README 完成安装、测试和核心流程执行

这里有一项需要提前强调：Phase 4 的经验复用实验，是我们创新性的核心证据，不应该等到项目最后才考虑如何验证。

可以在 Phase 0 就设计三类 Demo：

| Demo     | 目标          | 主要检验        |
| -------- | ----------- | ----------- |
| A：正常任务   | 需求到算法生成     | 端到端基础闭环     |
| B：故障任务   | 生成、失败、修复、重测 | Agent 自修复能力 |
| C：后续相似任务 | 检索并复用历史经验   | 知识沉淀的实际价值   |

建议再增加一个小规模对照：关闭历史经验检索，比较系统的修复次数、成功率或验证成本。对照需要使用相同输入和测试条件，不能只比较两条随意挑选的运行轨迹。

# 七、工程规范与实现约束

这些内容直接影响题目中占比 30% 的代码质量评分。

### 1. 项目结构

建议采用以下组织形式：

```
AlgoFactory/
├── src/algofactory/
│   ├── agents/          # Agent 角色及决策
│   ├── llm/             # API / Mock Provider
│   ├── knowledge/       # 抽取、图谱、检索
│   ├── planning/        # 候选方案与搜索
│   ├── generation/      # 代码生成与修复
│   ├── validation/      # 测试、指标、失败分类
│   ├── execution/       # 安全执行环境
│   ├── experience/      # 经验与版本管理
│   └── schemas/         # 统一数据模型
├── app/                 # Streamlit
├── configs/             # 任务及验证配置
├── data/                # 演示数据、知识文档
├── examples/            # 生成样例及报告
├── tests/               # 单元与集成测试
├── scripts/             # 初始化与运行脚本
├── docs/                # 架构及 Schema
├── README.md
├── requirements.txt
└── .env.example
```

不必为了目录完整而创建空模块。具体代码结构可以在 Phase 1 根据依赖关系细化。

### 2. 统一接口与结构化状态

推荐使用 Pydantic 定义 `TaskSpec`、`AlgorithmPlan`、`Candidate`、`ValidationResult`、`AgentDecision`、`ExperienceRecord` 等数据模型。

LLM 输出必须经过 Schema 校验，失败时允许有限次数重试；不能将未经验证的自然语言直接传给代码执行器。

### 3. 统一测试协议

所有算法候选必须使用相同的数据划分、目标字段、基础评价指标和资源预算。

模型选择和修复只能使用训练集与验证集。独立测试集用于最终性能报告，避免因为反复搜索导致测试信息泄漏。

### 4. 安全执行

生成代码在 Docker 隔离容器中运行，实施非 root 用户、只读挂载、网络禁用、资源与时间限制等措施。依赖环境使用预先批准的软件包集合，避免任意安装依赖。

这些措施降低执行风险，但不把 Docker 描述为绝对安全的沙箱。如果 Docker 不可用，允许 Mock 演示部分流程，但不能把未隔离的真实代码执行标记为安全通过。

### 5. Git 与可复现性

每个 Phase 完成后执行测试并形成独立提交。示例数据、Mock 响应、随机种子、依赖版本及报告生成命令都要进入仓库；API Key、临时容器文件和敏感数据不得提交。

# 八、对基础要求、进阶要求与加分项的最终取舍

| 类别             | 最终范围            | 原因             |
| -------------- | --------------- | -------------- |
| 基础要求           | 全部实现            | 交付底线           |
| 进阶：CLI/Web/API | CLI + Streamlit | 开发简单、易展示       |
| 进阶：多轮修复        | 实现              | Agent 核心能力     |
| 进阶：候选比较        | 实现              | 支撑算法方案选择       |
| 进阶：图谱可视化       | 实现              | NetworkX 可直接支持 |
| 进阶：报告生成        | 实现              | 结构化数据可直接导出     |
| 进阶：结果回写        | 实现              | 闭环必需           |
| 进阶：验证配置        | 二分类 + 轻量回归      | 证明机制可扩展        |
| 进阶：插件架构        | 模板和指标注册机制       | 控制开发复杂度        |
| 加分：多 Agent     | 三个逻辑角色          | 体现职责分工         |
| 加分：失败经验        | 实现并做复用实验        | 核心创新点          |
| 加分：版本管理        | 实现              | 支撑可追溯性         |
| 加分：代码安全        | 实现基础隔离          | 提升工程可信度        |
| 加分：自然语言解释      | 实现              | 便于面试展示         |
| 加分：Beam/MCTS   | 暂不实现            | 当前收益有限         |
| 加分：真实仓库抽取      | 暂不实现            | 需要额外处理复杂代码     |
| 加分：大规模性能优化     | 暂不实现            | 不属于核心验证目标      |

这里需要特别区分：三角色设计不等于一定要使用三个独立大模型。可以在统一编排器下调用同一个 Provider，但各角色必须具有独立输入、职责、输出契约和实际决策功能。

# 九、最终验收 Gate

建议最终采用五项 Gate，而不只是检查功能清单是否完成。

G1 — 功能完整性

题目所有基础要求均有实际交付物

G2 — 运行正确性

Mock 模式可重复完成；API 模式至少一次真实闭环成功

G3 — 验证可信性

测试规则独立、数据划分正确、指标由程序计算

G4 — 创新有效性

可展示验证驱动修复与历史经验复用证据

G5 — 交付复现性

独立环境安装、运行、测试和报告生成通过

只有 Gate 全部满足，才应将项目标记为最终完成。如果 API 服务不可用，也应如实标注哪些环节只经过了 Mock 验证。

## 十、当前 Phase 0 的结论

截至目前，我们可以先冻结以下决策：

项目问题： 从自然语言算法能力描述出发，利用结构化能力知识和验证反馈，完成算法生成、修复、评价及经验积累。

项目场景： 客户流失预测为主，表格分类为核心任务，轻量回归用于扩展性验证。

项目架构： Python 编排器、三个职责角色、LLM API/Mock Provider、SQLite/NetworkX、独立验证器与 Docker 执行环境。

核心创新： 不追求复杂的 MCTS，而是实现知识检索—候选规划—验证驱动决策—经验复用，通过可追溯的执行记录证明每项机制确实工作。

交付目标： 完整 GitHub 仓库、CLI + Web Demo、知识图谱、自动验证、多轮修复、版本管理、经验回写、文档与可复现示例。

下一步进入 Phase 1：架构与数据契约设计之前，建议首先完成 Phase 0 的正式规格文档，包括需求追踪矩阵、核心数据对象、端到端成功条件和三类固定演示案例。后续任何实现决策都以这份规格为依据，避免开发过程中不断扩张范围。

总体上，这个方案在你的本地 MacBook Pro 上可行，也能把笔试最重要的技术能力、代码质量、创新性和完整性四个评价维度结合起来。
